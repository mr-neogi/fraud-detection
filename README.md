# Credit Card Fraud Detection (FinTech)

A modular fraud-detection demo with a Streamlit dashboard, Isolation Forest, XGBoost + SMOTE, threshold tuning, evaluation reports, and single/batch scoring.

## Quick start

```bash
cd fraud-detection
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate
pip install -r requirements.txt
streamlit run app.py
```

The app runs with a synthetic, highly imbalanced dataset when `data/creditcard.csv` is absent. To use the Kaggle dataset, download `creditcard.csv` from **Credit Card Fraud Detection** on Kaggle and place it at `data/creditcard.csv`, then restart the app.

## Dashboard pages

1. **Overview** — portfolio KPIs, class donut, amount distribution.
2. **Data Explorer** — filters, amount/time charts, correlation heatmap and top class correlations.
3. **Model Training** — hyperparameters, SMOTE class counts, training and saved models.
4. **Evaluation Report** — model metrics, confusion matrices, PR curves, feature importance, Markdown/PDF exports.
5. **Live Predictor** — single transaction scoring and batch CSV scoring.

## Methodology and leakage controls

- Stratified 80/20 train/test split.
- RobustScaler is fitted on the training partition only and then applied to test data.
- SMOTE is applied only to the model-fitting portion of training data. The test set is never resampled.
- A validation slice is carved out of training data to select the decision threshold. Test metrics are computed only after threshold selection.
- Report fraud-class recall, precision, F1 and PR-AUC. Accuracy is shown only as a cautionary reference.

## Synthetic data note

The fallback generator creates the same schema and a rare fraud class so the application is runnable immediately. It is **not** a replacement for the Kaggle dataset: synthetic metrics are software-demo outputs and must not be interpreted as evidence of production performance.

## Limitations / next steps

- Validate on the official Kaggle data and then time-separated production-like data.
- Tune thresholds against estimated fraud loss, false-decline costs and analyst capacity.
- Compare SMOTE with class weighting and cost-sensitive learning.
- Monitor drift, calibration, stability, latency and customer impact.
- Consider SHAP explanations and human review before any operational use.

## Important

This is an educational prototype, not a production payment decision system. Do not use its predictions to approve or decline real transactions without independent validation, governance, security review and human oversight.
